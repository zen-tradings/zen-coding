**[3] User:** Here's my context. I'm a founder who also develops my own project, working with an engineer and a PM across different GitHub repos with different stacks. GitHub Issues holds our product todos; Notion is for docs when necessary; discussion happens in Slack or Zoom; settled architecture goes into spec.md. I want to speed up parallel development across projects. Each morning I lose track of priorities or how to coordinate my focus. And I don't want a separate UI or app to maintain — otherwise I'd just use Notion Calendar.
**Claude:** The "no new UI" constraint is the product thesis, not a limitation. The recording layer already works (GitHub/Notion/Slack/spec.md); what's missing is the decision layer: as a founder, where should attention go today — what's blocked on me, what needs my code, what needs a glance? Proposed a founder attention-scheduling layer: an agent pulls repo states daily, LLM synthesizes a morning brief with suggested priorities; I approve/adjust rather than enter data. Noted a read-only brief page satisfies the prototype requirement without creating input burden. Asked two questions: what actually determines my priorities, and what does an ideal morning look like?

**[4] User:** My priorities are composite: external pressure (others waiting on my progress) plus my own importance ranking. My ideal day is one where I get into a development state quickly.
**Claude:** The second answer matters most: the friction isn't only ranking, it's the 20–40 minutes of context reconstruction per project switch. Proposed two-part shape — Morning Brief (external signals: who's waiting on me, from review requests/mentions/blocking issues; plus my declared weekly focus as ranking input) and Context Launcher (per project: recent commits, open PR state, issue summaries, relevant spec section, "you stopped at X; next step Y" — pasteable into Claude Code to start coding in 5 minutes instead of 30). Noted triple fit with the JD's "improve the AI developer experience." Proposed 48h cuts: GitHub only; manual weight config; context pack as stretch.

**[5] User:** Can you explain what a "context launcher" would actually do?
**Claude:** Explained: knowing what to work on ≠ being able to start. Re-entering a cold project costs ~20 minutes of reading commits, PR comments, issues, specs. The launcher auto-generates a handoff pack per project (recent commits summary, open PR status, key issue state, relevant spec section, one-line "you stopped at X, next: Y") from the GitHub API + LLM summarization — and doubles as a ready-made opening context for a Claude Code session. Offered a lighter fallback (per-task expandable context summary) if it felt out of scope.

**[8] User:** Does my final direction fit their ask, or has it drifted off-topic?

**[9] User:** Where exactly is the "task tracking" reflected in this design?
**Claude:** Three layers: (1) per-task state tracking, auto-inferred from GitHub activity instead of hand-updated; (2) cross-repo aggregated view — the classic tracker value (everything in one place) without manual data transfer; (3) tracking attention drift — declared intent vs. actual behavior — which no traditional tool tracks. Suggested adding a plain "All Tasks" aggregated list view: near-zero cost, makes the tracker identity visible at a glance.

**[10] User:** Given those three tracking layers, how should the UI be structured? *(Pasted back the three-layer tracking explanation.)*
**Claude:** One page, three zones mapping the three layers — rendered a wireframe: (1) Today's brief: 3–5 ranked cards, each with a one-line reason (the LLM's key output) and category tags Unblock / Drift / Glance; (2) Attention budget: per-project bars, actual fill vs. declared tick mark; (3) All tasks: flat filterable list as the tracker anchor. Design decisions: single page, read-only, no add-task button (the absence is the thesis); reasons over raw charts; information density decreasing downward. Advice: ≤20% of build time on UI; reason quality outweighs polish.

**[11] User:** Can the ranking model also account for my own importance judgments, objective build difficulty, and importance-vs-reward alignment — with maximizing parallel development as the goal?
**Claude:** Warned of factor explosion (a five-factor model where three factors have no data source), then fit each in without new input burden: importance → read existing GitHub P-labels (triage-time habit, not new entry); difficulty → LLM rough sizing (quick / half-day / multi-day); reward → merged into importance (same declaration source for a single-user system — a documented cut). Parallel development is the objective function, not a factor: (i) unblock-others tasks always first (highest team-throughput leverage), (ii) own deep work ranked by importance × drift, (iii) difficulty used for intraday packing (gap tasks fill meeting gaps). Declared the model frozen.

**[12] User:** Can you redesign the UI to reflect this model?
**Claude:** Rendered wireframe v2: brief restructured into explicit tiers — Unblock section (red accent; each card shows leverage "blocks N people" and cost "~1h/~15m"), Deep work section (reason cites P-label + drift + idle days), a slim Gap-tasks row; chips on each card expose the model at a glance; All tasks rows gain waiting-on-you and P-label badges. Deliberately absent: drag-reorder, checkboxes, chart pages — completion state belongs to GitHub; the system stays read-only.

**[13] User:** How is the "attention budget — declared vs. actual" calculated, and how is the declared side set?
**Claude:** Declared: manual weekly config file (YAML — repo:percentage; 30 seconds each Monday); deliberately no settings UI. Actual: GitHub activity as a proxy — collect my last-7-day events per repo (commits, reviews, comments), weight by type (commit 3 / review 2 / comment 1), normalize to shares. Pre-answered three objections: proxy noise (directionally sufficient for drift detection, not hour-accounting; v2: diff-size weighting, Claude Code session logs); weight calibration (prior estimate corrected against subjective experience — an eval loop); invisible thinking-work (v1's honest boundary — and exactly why declared must exist as the channel for the unmeasurable). Framed as portfolio drift monitoring: target allocation vs. mark-to-market, daily rebalancing prompt.

**[14] User:** What's the data pipeline behind the Today's Brief?
**Claude:** Three-stage pipeline: (1) raw data — GitHub API only (issues, PRs, review requests, mentions, blocked-by references, commits; PAT auth covers private repos; zero manual entry); (2) two signals computed in deterministic code, not LLM (numbers belong to code; narrative belongs to the LLM — a documented decision); (3) LLM synthesis — structured signal data in, ranked JSON out ({rank, category, headline, reason citing concrete data}), rendered as the cards. Stateless v1: fetch-on-load, no database. Suggested the pipeline as the build's session structure: fetch → signals → LLM → UI, each step verifiable.

**[15] User:** The data sources are GitHub-only — why not include Notion or Slack records?
**Claude:** Correct — the deliberate cut from discovery, now argued fully: signal density (structured GitHub fields vs. unstructured chat requiring lossy LLM extraction); my own workflow already funnels confirmed work into GitHub (Slack/Notion are upstream; GitHub is the confluence — sampling there covers confirmed work); 48h engineering reality (OAuth, workspace approvals); demo-ability. Honest blind spots: verbal commitments, DM-level blockers, document-type tasks. v2 path ranked by signal value: directed Slack capture (only @me + request-shaped, flagged unconfirmed) > Claude Code session logs > Notion. Advice: present data sources as a tiered evaluation framework, not a feature count.

**[16] User:** Is the "declared" side something I set manually?
**Claude:** Yes — by definition: declared is intent, which exists only in my head; if it could be inferred it would equal actual and drift would vanish. Form: weekly config file (budgets + a free-text focus_note fed to the LLM so reasons can quote my own words). Precision on the thesis: not "zero input" but "no transfer of already-existing information" — the weekly declaration is new information entering the system through its only possible channel. Bonus: git history versions my intent over time.

**[17] User:** Does the free-text note influence the importance weights? I want an unstructured way to express my intent.
**Claude:** Upgraded the design: free text becomes the primary intent channel — numeric budgets can't express rules ("data-pipeline: don't let it block anyone") or hard constraints ("demo env by Thursday"). Architecture: weekly natural-language note → LLM "intent compiler" → structured {weights, rules, constraints} → shown for confirmation ("system's understanding") with manual override → cached and reused deterministically for the week's daily rankings. Key points: compile once, reuse daily (no ranking drift); LLM translates, human confirms; numbers remain an optional explicit override. Positioned as the submission's strongest AI-native signature: natural language as configuration, with LLM uncertainty tamed by system design.

**[18] User:** Is the "All tasks (23)" section purely objective fact, or does it include inference?
**Claude:** Mostly, with a precise line: facts (existence, title, state, assignee, timestamps, review requests, my own P-labels — GitHub fields verbatim) vs. inference (waiting-on-you badge — partly text-parsed; effort estimates — LLM-guessed). Noted this answers a finance firm's instinctive "what if the LLM is wrong" — architecturally, not by prompt confidence.
